# 앱 전체 설명 문구 한 번 더, 이번엔 "무슨 말인지 모르겠다"를 기준으로

## Context
사용자: "설명들 좀 어케 더 못 다듬냐. 여전히 불명확해. 전반적으로 다." 처음에 한 번 전체를 새로 썼는데도 같은 불만이 나왔어요. 그때 기준은 "해요체, 전문용어 금지, 안전 정보 유지"였고, 문장은 부드러워졌지만 **독자가 모르는 말이 그대로 남은 채** 문장만 정리됐어요. 지금 화면에서 보이는 불명확함은 이런 유형이에요.

| 유형 | 지금 문구 | 왜 불명확한가 |
|---|---|---|
| 모르는 말 | "심사에 낸 앱을 보관한 파일이에요", "지워도 기기를 연결할 때 다시 받아요" | 무슨 앱·무슨 기기인지, 왜 그게 파일로 남는지 모른다 |
| 뭉뚱그림 | "개발 중 앱을 실행하며 생긴 임시 파일이에요", "개발용 파일", "임시 파일" | 안에 뭐가 들었는지 모르니 지워도 되는지 판단이 안 된다 |
| 부정확한 지칭 | "Mac을 움직이는 프로그램과 잠깐 실행된 프로그램을 합친 값이에요. App Store 버전에서는 각각 나눠 볼 수 없어요" | 합친 값이 무엇인지 이해가 안 되고, 앱 사정(스토어 버전)을 사용자에게 설명한다 |
| 같은 틀 반복 | CPU 탭 "…macOS 기본 프로그램이에요." 40여 개, "바빠요/조용해져요" 20여 개 | 모두 같은 말이라 아무것도 구별되지 않는다 |
| 낯선 단위 | "CPU 정보는 총 8개, 성능 4개, 효율 4개예요" | 무엇의 개수인지(코어) 모른다 |
| 판단 근거 없음 | "~일 수 있어요" 남발 | 지워도 되는지 결론이 안 난다 |

## 새 기준 (v2) — `.design-bounce/copy/style.md`에 추가
1. **모르는 말은 풀어 쓰거나 뺀다.** 독자가 처음 보는 명사가 있으면 그 말 없이 다시 쓴다. "심사에 낸 앱" → "App Store에 올리려고 만든 앱 파일". "기본 프로그램" 반복 → 이 프로그램이 **실제로 하는 일** 한 가지.
2. **한 줄 = 무엇이 + 지우면 어떻게 되는지.** 뭉뚱그린 분류 이름(임시 파일, 개발용 파일, 기록) 대신 **어디서 생기고, 지우면 무엇이 일어나는지**를 말한다. 예: "Xcode가 앱을 만들 때 쌓아 둔 중간 결과예요. 지우면 다음 빌드가 처음보다 오래 걸려요".
3. **결론을 먼저.** 지워도 되는지, 조심해야 하는지를 문장 앞에 둔다. 가능성은 "~일 수 있어요" 하나로 얼버무리지 않고, 확실한 것은 확실하게, 모르는 것은 "내용을 확인하세요"로 행동을 준다.
4. **앱 내부 사정은 말하지 않는다.** App Store 버전, 샌드박스, 권한 구조는 사용자가 알 필요 없다. 결과(못 보여 준다)와 다음 행동(허용한다)만.
5. **같은 문장을 되풀이하지 않는다.** CPU 설명처럼 항목이 많은 곳은 항목마다 **그 프로그램만의 사실**을 쓴다. 공통 틀("~하는 macOS 기본 프로그램이에요")을 쓰지 않는다.
6. **낯선 단위는 일상 말로.** "CPU 8개" → "계산을 맡는 일꾼이 8명이에요"처럼 말하거나 아예 뺀다.
7. 설명 칸은 좁다(안전 한 줄, 주의 두 줄, 약 28자 이내). 줄에는 한 가지만.

## 방법
화면 문구는 약 160개(CPU 프로그램 설명 82개 포함)예요. 코덱스 4개를 **소스 파일 묶음별로 동시에** 돌려요. 카탈로그(`Localizable.xcstrings`)는 동시에 쓰면 충돌하므로, 코덱스는 **Swift 소스만 고치고 번역 패치를 JSON 파일로 따로 써요**. 내가 합쳐서 카탈로그에 넣어요.

|---|---|---|

| B. 항목 설명·보호 사유 | `Scan/*Scanner.swift`, `Model/CleanupScope.swift`, `Safety/RemovalVerdict.swift`, `ProtectedPaths.swift`, `UserFolders.swift`, `FolderAccess.swift` | 약 45 |

코덱스 지시는 이래요.
- 기준 v2와 **고쳐 쓴 예시 8쌍**(내가 먼저 써 준다)을 준다. 어미만 바꾸는 것은 실패라고 못 박는다.
- 문구마다 **독자 질문 하나**에 답하게 한다: "이 줄만 읽고 지워도 되는지 알 수 있는가?" 그렇지 않으면 다시 쓴다.
- 사실을 지어내지 않는다: 소스·주석에서 그 항목이 실제로 무엇인지 읽고, 모르는 것은 일반 사실로만 쓴다.
- 보간(`\( )`, `%@`, `%lld`)은 개수와 뜻을 유지한다. 소스 구조·로직·테스트는 안 건드린다.
- 출력은 소스 수정과 `.design-bounce/copy/patch-{A,B,C,D}.json`(`{옛 키: {"ko": 새 한국어, "en": 새 영어}}`).

## 내가 하는 일
1. 합치기: 패치를 카탈로그에 넣고 옛 키를 지운다. `scripts/l10n.sh check`로 번역 없음·소스에 없음 0 확인.
2. **읽고 고치기**: 코덱스 결과를 묶음마다 전부 읽는다. 사실이 바뀐 곳, 길이가 칸을 넘는 곳, 여전히 모호한 곳을 직접 고친다. 이번엔 이 단계를 건너뛰지 않는다.
3. **깨지는 테스트 고치기**: 문구를 문자열로 비교하는 테스트가 많다(이전 전체 정리 때 107건). 값을 새 문구로 바꾸는 것이 아니라 가능하면 소스의 같은 상수를 참조하게 고친다.
4. **화면으로 보기**: 샌드박스 빌드를 한국어·영어로 캡처해서 정리 목록, 확인창, CPU 탭, 공간 보기를 읽고, 좁은 칸에서 잘리는 곳을 찾는다.

## 개발 Phase 계획

### Phase 1: 기준과 예시
**목표**: 코덱스에게 줄 기준 v2와 고쳐 쓴 예시를 만든다.
- Step 1: `style.md`에 v2 추가, 고쳐 쓴 예시 8쌍 작성 — 기준이 파일에 있고 예시가 7개 기준을 모두 보여 준다

### Phase 2: 코덱스 4묶음
**목표**: 소스 문구와 번역 패치를 얻는다.
- Step 1: A·B·C·D를 동시에 돌린다 — 4개 결과 파일과 패치 JSON이 생김
- Step 2: 패치를 카탈로그에 합친다 — `l10n.sh check` 번역 없음 0, 소스에 없음 0

### Phase 3: 검토와 수정
**목표**: 읽어서 고치고 테스트와 화면으로 확인한다.
- Step 1: 묶음별로 읽고 직접 고친다 — 모호한 문구 목록이 비어 있음
- Step 2: 깨진 테스트 수정 — `swift test` 통과
- Step 3: 샌드박스 캡처(한·영)로 잘림과 읽힘 확인 — 캡처에서 줄이 잘리지 않음

## 검증

## 위험
- 규모가 커서 코덱스가 사실을 바꿀 수 있다. 그래서 4묶음 전부를 내가 읽고, KnownProcess는 항목별로 대조한다.
- 문구가 길어지면 좁은 칸에서 잘린다. 칸 길이 기준(약 28자)을 지시에 넣고 캡처로 확인한다.
- 문구 비교 테스트가 많이 깨진다. 소스의 같은 상수를 참조하게 고쳐서 다음번에는 안 깨지게 한다.
- 이미 두 번째 정리라 "또 바꿨는데 별로"가 될 수 있다. 그래서 이번에는 **기준 자체를 불명확함의 유형으로 바꿨고**, 결과를 사용자가 바로 볼 수 있게 설치한다.
